## 情境（Context）

系统需从用户上传的 PDF 和照片中抽取简历信息。简历包含敏感个人信息，架构约束要求只发送给批准的模型服务。Dev Lead 确认 `deepseek-flash` 已获批且支持目标输入能力。

## 选项（Options）

### 选项 A（已选）：获批 DeepSeek Flash 直接多模态理解

- 优点：减少额外 OCR 依赖及处理链路；只使用已批准模型。
- 缺点：模型 API、目标格式及供应商数据处理配置仍须在集成环境核实；能力不可用时无解析回退。

### 选项 B（未选）：本地 OCR/文本提取后调用模型

- 优点：能在视觉能力不足时提供替代解析路径。
- 缺点：用户明确选择不使用 OCR 回退；增加新组件与运维维护面。

### 选项 C（未选）：调用其他视觉模型

- 优点：可在主模型不支持时继续处理。
- 缺点：未获批准，简历数据不得发送给该服务。

## 决策（Decision）

仅通过 backend `clients` 层调用获批的 `deepseek-flash` 直接理解支持的 PDF/照片输入；供应商不得将输入用于训练，并按获批的最短留存期限或不留存策略处理。若目标环境能力或授权不满足要求，则阻断解析并反馈，不切换 OCR 或其他模型。

## 后果（Consequences）

- 正面：处理链路和数据外发边界清晰。
- 负面：模型服务能力或策略变更可能使解析不可用。
- 需跟进：impact-analyzer/实现阶段验证具体 API 输入格式、授权配置及供应商训练/留存策略；测试数据必须合成或脱敏。

## 修订记录

### 2026-11-10 修订 1：PDF 先在本地转换再提交（DL 裁决，随 HR_PR-1 任务 1.8 审查确认生效）

- **触发**：任务 1.8 用合成文档实测，`deepseek-flash` 的 API 只接受 webp / png / jpeg / gif 图片，PDF 的各种写法（`file` 块、`image_url`、`input_file`、Files API）都被拒绝。原决策"直接理解 PDF"在接口层面不成立，与 C-01"已实测支持 PDF"的结论不符。
- **决策**：
  - 仍然**只使用 `deepseek-flash`**，不使用同一凭证下可见的其他模型（如 `deepseek-v4-pro`），不使用 OCR。
  - PDF 在 backend `clients` 层本地转换为模型可识别的输入后再提交：
    1. **文本层优先**：用 `pypdfium2` 提取每页文本层，有效文本足够时以 text 块发送（字符准确，token 低）；
    2. **渲染兜底**：无文本层或文本过少的页面渲染为 PNG（长边约 1600px），以图片发送；
    3. 最多处理前 5 页。
  - 照片（PNG / JPEG）仍直接以图片发送。
  - 记录每次调用的 token 用量（只记数字），用于监控消耗。
- **理由**：只使用一个获批模型，外发边界不变（B-02）；文本层避免手机号、邮箱的视觉误读，同时降低 token；渲染路径覆盖扫描件；契约（OpenAPI 0.1.1）和 frontend 不受影响。
- **影响**：新增依赖 `pypdfium2`；backend design §6 / §7.2、tasks 1.8、AGENTS.md 同步修订；精度与 token 数据以任务 1.8 的 spike 证据为准。
