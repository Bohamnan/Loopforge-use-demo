title: 对话修改与问答由获批模型理解，修改以"建议 + 用户应用"生效
status: ACCEPTED
date: 2026-11-11

## 情境（Context）

v2（HR_PR-1-CRv2）要求用户能用自然语言修改简历字段、并就简历内容与填写流程提问。ADR-006 选定"不解析自由文本、不设文本框"，已不满足需求。约束：只能用获批的 `deepseek-flash`（B-02）；不得猜测补全（B-04）；对话内容属敏感信息（B-03）。

## 选项（Options）

### 选项 A（已选）：模型理解对话，输出"回复 + 结构化修改建议"，用户点"应用"后生效
- 优点：交互最自然，提问与修改可在同一条消息里处理；模型只产出建议，不直接写入，最终写入仍走现有字段校验与分区更新路径；用户逐条确认，可追溯。
- 缺点：每条消息一次模型调用（时延数秒、产生 token 成本）；模型可能误解或编造，需要 backend 侧确定性校验兜底；要防简历文本或用户输入中的提示词注入。

### 选项 B（未选）：固定句式"字段名 改成 新值"由前端规则解析
- 优点：无模型调用、确定性强。
- 缺点：不能回答问题；列表类字段难以表达；句式稍有变化即失败，体验仍然呆板。未选原因：不满足 PRD #5 问答，也达不到"对话"的基本体验。

### 选项 C（未选）：模型理解后直接写入字段，事后展示修改卡片并支持撤销
- 优点：少一次点击。
- 缺点：误解析的值会先进入草稿并被视为已确认，违背 B-04 的"不猜测"精神。未选原因：DL 确认采用"应用后生效"。

## 决策（Decision）

backend 新增对话接口：把当前简历字段（结构化 JSON）与本会话最近的对话记录发给 `deepseek-flash`，要求返回"回复文本 + 修改建议列表（字段、新值）"；backend 对建议做确定性校验后存为待应用建议，用户点"应用"时按现有字段更新路径写入并视为已确认。

## 后果（Consequences）

- 正面：满足 PRD #3/#5；分区就地编辑（ADR-006 的分区部分）继续保留，两种方式修改同一份草稿。
- 负面：新增模型调用与提示词维护成本；同步等待数秒（沿用 ADR-002，前端显示"思考中"）。
- 需跟进（LLD 必须落实）：
  1. 建议字段只能是简历模型白名单字段；新值必须通过与分区编辑相同的字段校验，不通过则不提供"应用"。
  2. 姓名、手机号、邮箱的建议新值必须出现在用户本条消息中（规范化后比对），否则 backend 丢弃该建议——用确定性规则守 B-04，不依赖模型自觉。
  3. 提示词与注入防护：简历内容与用户消息都作为数据放在分隔标记内；模型输出按固定 JSON 结构解析，解析失败按"回复失败"处理，不写入任何字段。
  4. 问答范围：只答本简历与填写流程；范围外（评价简历、岗位匹配等）拒答。
  5. 对话内容、模型回复不进日志（B-03），只记 token 用量等白名单字段。
  6. 原始简历文件不在对话中重复发送，只发送结构化字段，控制请求体与成本。
