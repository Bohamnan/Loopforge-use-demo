title: 以规范化“姓名+手机号+邮箱”作为幂等键，确认保存幂等并返回 already_saved
status: ACCEPTED

## 情境（Context）

系统无账号体系，确认保存接口可能被重复提交（重试、重复点击、并发）。裁决 C-10/D-02 要求同一个人不重复入库。该决定固化为正式库的唯一约束和对 frontend 的契约（HTTP 状态与 `already_saved` 字段），上线后难以回退。

## 选项（Options）

### 选项 A（已选）：规范化 (姓名, 手机号, 邮箱) 联合唯一 + 先查后写 + 冲突回查
- 优点：无需账号即可识别“同一个人”；数据库唯一约束兜底并发；契约简单（201 新增 / 200 `already_saved=true`）。
- 缺点：同名同号同邮箱被视为同一人，信息有变化的重新提交会被丢弃而不是更新；规范化规则变更需要数据迁移；确认成功后响应丢失的重试会得到 `draft_not_found`（D-01，POC 接受）。

### 选项 B（未选）：以草稿 id 作为幂等键
- 优点：实现最直接。
- 未选原因：草稿在确认后即删除（C-11），无法对“重新上传同一份简历”幂等；不能防止同一人多次上传产生多条记录。

### 选项 C（未选）：允许多条，不做唯一约束
- 优点：最简单。
- 未选原因：与 DL 裁决 C-10 冲突，会产生重复记录。

### 选项 D（未选）：命中后覆盖已有记录
- 优点：保留最新信息。
- 未选原因：已确认记录不可修改（C-11）；覆盖涉及历史版本与原文件替换，超出本期范围，且会放大 B-05 风险。

## 决策（Decision）

正式库对规范化后的 (姓名, 手机号, 邮箱) 建联合唯一约束；确认保存按此键幂等，命中时不新增、不覆盖、丢弃本次内容，返回已有记录 id，HTTP 200 并带 `already_saved=true`，首次保存返回 201。

## 后果（Consequences）

- 正面：重复提交与并发都收敛到同一条记录；契约对 frontend 清晰。
- 负面：规范化规则（D-02/O-04）成为长期数据契约；同一人的更新信息无法通过本接口覆盖；“首次成功但响应丢失”的重试体验退化（`draft_not_found`）。
- 需跟进：后续若支持更新/删除已确认简历，需另立需求并重新评估本键；规范化规则变更必须附带迁移方案。
- 关联：C-10、D-01、D-02、D-04、O-08；`02_schema/sql_ddl_resume.md` §2.2；`03_api/api_design_resume.md` §3.4。
