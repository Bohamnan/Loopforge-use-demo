## 情境（Context）

架构约束 B-05 要求简历记录与原始文件一致，不得出现“有记录无文件”或“有文件无记录”。文件存放在项目 `file/` 目录，记录在 SQLite，二者之间没有分布式事务。归档文件命名与目录布局一旦有数据后难以变更。

## 选项（Options）

### 选项 A（已选）：复制到 tmp → 单事务写库 → 提交后原子重命名；启动时对账
- 做法：文件以 `.{resume_id}{ext}.tmp` 先复制并 `fsync`，在 `BEGIN IMMEDIATE` 事务写入记录，提交后 `os.replace` 为终态名 `{resume_id}{ext}`；启动对账：有记录且仅有 tmp → roll-forward；有 tmp 无记录 → 删除；有终态文件无记录 → 删除；有记录无任何文件 → 仅告警。
- 优点：提交前的失败只需清 tmp；提交后的崩溃可确定性前滚；文件名由服务端生成，防路径穿越且与记录 id 一一对应，对账无需额外清单。
- 缺点：存在“已提交未重命名”的短暂窗口，期间终态文件不存在（读取方本期不存在）；依赖启动对账完成修复；“记录存在而文件已丢失”无法自动修复。

### 选项 B（未选）：先重命名为终态文件，再写库
- 优点：永远不会出现“有记录无文件”。
- 未选原因：与 REQ-BE-04.3 规定的“提交后再重命名”不一致；崩溃会遗留终态孤儿文件，清理时需区分“进行中”与“已孤儿”。

### 选项 C（未选）：文件内容存入 SQLite BLOB
- 优点：原子性由数据库保证。
- 未选原因：违背“原始文件存放在项目 file 目录”的既定设计；10 MB 文件放入 SQLite 影响库体积与备份。

### 选项 D（未选）：引入两阶段提交/外部事务协调
- 未选原因：POC 规模不值得；增加组件。

## 决策（Decision）

采用选项 A：归档文件以 `{resume_id}{ext}` 命名，保存顺序为“复制 tmp → 事务写库 → 原子重命名”，并在每次进程启动、对外服务前执行对账。

## 后果（Consequences）

- 正面：B-05 在失败与崩溃两类场景下均可收敛；无需额外元数据文件。
- 负面：必须单进程启动并保证对账先于服务；“记录存在而文件丢失”只能告警，需人工处理。
- 需跟进：部署需保证 `file/` 与 tmp 在同一文件系统；若将来改为对象存储或多实例，需重新设计。
- 验证：`design.md` §9.3 故障注入测试逐点覆盖。
