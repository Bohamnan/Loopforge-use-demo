字段说明：

- **TC_ID**：与 `qa_test_cases.md` 完全一致，不得自拟。
- **维度**：AT、E2E、NEG、PERM、REG、UAT 之一，与 TC_ID 中的维度一致。
- **执行方式**：用例的执行是否经过大模型。用模型桩（mock、固定返回）填"模型桩"；调用真实模型填"真实模型"；用例不涉及模型填"N/A"。同一用例两种方式都跑过，分两行记录。
- **结果**：只能是通过、失败、阻塞三者之一。失败 = 实际结果与 Expect 不符；阻塞 = 因环境、数据或前置缺陷无法执行，必须写明阻塞原因。
- **证据**：失败和阻塞必填；通过项建议填。可用截图路径、接口响应片段、日志片段或录屏路径，路径相对本报告所在目录。证据中不得出现密钥、token，手机号、身份证等敏感信息须脱敏。
- **关联 bug**：失败项必填，阻塞项若由某个缺陷引起也要填；编号规则沿用项目缺陷登记方式，本模板不规定编号。

## 失败项转交 bug-fixer

1. QA / Dev Lead 把上方对应小节（TC_ID、前置条件、复现步骤、预期与实际结果、证据）交给所属 Workbench 的工程师。
2. 工程师在自己的 Workbench 会话中执行 `bug-fixer`，把该小节作为"测试人员提交的复现步骤"输入。`bug-fixer` 不依赖运行环境，仅做静态分析和最窄范围修复，并补回归测试。
3. 修复完成后，工程师把状态改为"已修复待回归"。
4. QA / Dev Lead 重跑关联的全部 TC_ID（执行方式与首次一致），在执行明细中追加新一行（保留首次失败行，不覆盖），结果通过则把状态改为"回归通过"。
5. 重跑仍失败时，回到第 1 步，缺陷小节追加"第 N 次回归失败"及新的实际结果。
6. 同一 bug 多次修复仍无法回归通过，或修复需要改动需求 / 接口契约，转 `requirement-change-router`，不再走 `bug-fixer`。
