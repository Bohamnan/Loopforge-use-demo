## §1 业务目标与约束

### 核心业务目标

用户上传 PDF 或照片类简历后，系统同步解析内容并整理为预设 HR 简历模型，通过对话允许用户逐项校对。用户明确确认且姓名、手机号、邮箱均齐全后，系统保存结构化简历记录及其原始文件关联。

<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
用户可以用自然语言修改字段（模型给出修改建议，用户"应用"后生效）并就本简历与填写流程提问；同一浏览器可查看、继续、删除历史会话；所有人可只读查看已归档简历及其原始文件。

### 关键非功能需求

- **交互时效**：上传后同步完成解析并返回待校对结果；本阶段选择同步处理，不引入后台任务状态流程。具体响应时间目标尚未定义。
- **首期规模**：最多约 5 人同时处理简历。
- **文件边界**：仅 PDF、JPG/JPEG、PNG；单文件不超过 10 MB。
- **会话保留**（v2 修订）：会话（含未确认草稿与对话记录）保存在服务端，同一浏览器可恢复；**不自动清理**，只能由用户手动删除（ADR-008）；不将简历内容存入浏览器本地。
- **正式归档**：正式简历记录与原始文件均存放在项目本地存储，使用受控主机/磁盘加密；正式记录无自动到期清理。
- **模型数据处理**：DeepSeek Flash 仅用于推理，不得将简历输入用于训练；供应商侧按已批准的最短期限或不留存处理。DeepSeek 已获项目方批准，Dev Lead 确认该模型支持所需的 PDF/图像理解能力。
- **隐私与安全**：简历是敏感个人信息，只发送给批准的模型服务；不得在日志或错误响应中泄露简历原文或敏感信息；测试仅用合成或脱敏数据。
- **身份与恢复**（v2 修订）：不要求用户账号；使用 HttpOnly Cookie 中的随机浏览器标识（长期有效、随访问续期），用于在同一浏览器列出与恢复会话（ADR-008）。
- **对话时效**（v2 新增）：每条对话消息同步调用一次模型，前端显示"思考中"，不流式输出；具体时延待实测。
- **访问边界**（v2 新增）：无账号与权限控制；服务只监听本机地址，已归档简历对本机所有使用者可见（ADR-009，已接受风险）。
- **待明确的 NFR**：峰值之外的扩展规模、精确响应时间/SLA、供应商实际留存时长，须在影响分析/技术设计中核实，不在此虚构阈值。

### 命中的架构约束

| 约束 | 本方案的落实方式 |
|---|---|
| B-01 密钥与凭证 | 模型凭证仅由 backend 服务端环境配置提供，不进入前端、日志、仓库或测试夹具。 |
| B-02 外部服务出口 | 仅经 backend 的 `clients` 层调用获批的 DeepSeek Flash；v2 的对话理解同样只发往该模型。 |
| B-03 敏感信息不进日志/错误 | 只记录请求标识与必要的非敏感诊断信息；对用户返回通用错误，不包含简历原文。v2：对话消息、模型回复、修改建议的值一律不进日志。 |
| B-04 用户确认后才正式入库 | 未确认内容仅在服务端临时草稿存储；用户明确确认且核心信息齐全后才写入正式 SQLite 数据库。v2：模型只产出修改建议，用户"应用"后才写入草稿；姓名、手机号、邮箱的建议值必须出现在用户消息中，否则丢弃（ADR-007）；对话中说"确认提交"不直接保存。 |
| B-05 原始文件与记录一致 | 原始文件在项目 `file` 目录归档；最终保存流程必须保证文件与简历记录一起成功，失败时回滚或补偿清理，不能留下孤立记录/文件。 |
| B-06 简历隐私 | 仅调用获批模型；供应商不得训练；开发/测试仅使用合成或脱敏简历。 |
| F-01 前端不持有凭证、不直连外部服务 | 前端仅调用 backend HTTP API，不接触模型密钥、外部服务或持久化存储。 |
| F-02 浏览器不保存敏感数据 | 简历内容与对话内容只在前端运行时内存展示；浏览器持久化仅包含不透明的 HttpOnly 浏览器标识 Cookie（v2）。 |
| F-03 用户确认前不显示已保存 | 只有 backend 确认保存成功后前端才显示成功反馈。 |
| 跨 Workbench 契约约束 | backend 维护 OpenAPI 契约，frontend 按契约消费；契约变更需 cross-workbench-reviewer 审视。 |

## §3 数据流设计

1. **选择与上传**：用户在 frontend 选择不超过 10 MB 的 PDF、JPG/JPEG 或 PNG；frontend 通过统一 API 封装层向 backend 发起同步 HTTP 上传，采用 multipart/form-data。前端不保存简历内容到浏览器持久存储。
2. **校验与暂存**（v2 修订）：backend 校验文件类型和大小，将原始文件写入服务端本地临时区域，并在当前浏览器标识下创建一个会话（浏览器首次访问时签发 HttpOnly 浏览器标识 Cookie）。会话不自动清理。
3. **模型解析**：backend 经 `clients` 层将文件内容同步发送给获批的 `deepseek-flash`，由其直接理解 PDF/图像并生成简历模型候选结果。供应商侧不得训练，按获批的最短期限或不留存策略处理数据。若当前授权模型能力不可用或拒绝该输入，不调用 OCR 或其他模型，停止该次解析并向用户返回不含敏感内容的错误提示。
4. **对话校对**：backend 将候选结构化草稿和待补充/待确认项返回 frontend；用户通过 REST/JSON 回复和修正字段。frontend 仅在运行时内存展示结果，刷新或重新打开同一浏览器时凭 HttpOnly Cookie 从 backend 恢复草稿。姓名、手机号、邮箱三项为正式保存前必需信息；其他简历字段可空。
   - **对话消息**（v2 新增）：用户发送自然语言消息 → backend 把当前结构化字段与本会话最近的对话记录发给 `deepseek-flash` → 模型返回回复文本与修改建议 → backend 校验建议（字段白名单、字段规则、三项必填须出现在用户消息中）并保存消息与建议 → 前端展示回复与修改卡片。用户点"应用"后，backend 按分区编辑相同的更新路径写入草稿并视为已确认；"取消"则标记建议为已取消。
5. **明确确认与正式保存**：用户明确确认后，backend 校验核心字段，协调将原始文件归档到项目 `file` 目录并在 SQLite 写入结构化简历及文件关联。实现必须通过事务、暂存/原子替换与失败补偿等 LLD 机制保证 B-05，不得在局部失败后留下孤立数据。仅全部保存成功后，backend 返回成功，frontend 才提示已保存。
6. **会话留存与手动删除**（v2 修订）：会话不自动清理。用户删除校对中的会话时，删除其草稿、对话记录与临时文件；删除已保存的会话时只删除对话记录。确认保存后会话转为"已保存"并关联正式简历记录，草稿临时文件在归档成功后可删除。已确认简历记录及原始文件无自动到期清理，也不提供删除。
7. **历史会话**（v2 新增）：frontend 打开时凭浏览器标识 Cookie 读取本浏览器的会话列表（名称、状态、最近活动时间）；选择会话后读取该会话的简历信息与对话记录。已保存会话的简历内容从正式库读取，只读展示。
8. **已归档简历查看**（v2 新增）：frontend 读取正式库的简历列表（按保存时间倒序）与详情；原始文件由 backend 按记录关联路径读取后返回给浏览器打开或下载。

**时效与规模**：交互采用同步请求/响应；首期约 5 人并发，每份文件最多 10 MB。端到端响应时间、超时阈值和重试策略在技术设计阶段依据模型实测确认。

## §5 对下游各 Workbench 的输入约束

### Backend

- 采用工作台已确认的 Python 3.11、FastAPI、Pydantic v2、SQLite 技术基线；遵循 `api → services → repositories / clients` 分层。
- 对前端提供 REST/HTTP/JSON 与 OpenAPI 契约；文件上传采用 multipart/form-data。backend 是契约维护方。
- 仅通过 `clients` 调用获批的 `deepseek-flash`。直接 PDF/照片理解是选定方向；若模型能力或授权在实现环境中不可用，应阻断解析并反馈，不得暗中切换 OCR 或其他供应商。
- 正式简历记录只在用户明确确认且姓名、手机号、邮箱均齐全后写入 SQLite；其他字段允许为空。
- 未确认草稿与正式简历数据库分离，服务端本地暂存；**v2：不自动清理，取消 7 天清理调度；会话归属于 HttpOnly 浏览器标识 Cookie，可多会话、可手动删除**（ADR-008）。访问任何会话必须校验其归属。
- v2：对话接口只调用 `deepseek-flash`；模型输出按固定结构解析，修改建议须经字段白名单与字段规则校验；姓名、手机号、邮箱的建议值须出现在用户本条消息中，否则丢弃；建议只在用户"应用"后写入（ADR-007）。问答只限本简历与填写流程。
- v2：已归档简历提供只读列表、详情与原始文件下载；文件按记录关联路径读取并校验位于归档目录内；服务只监听本机（ADR-009）。
- v2：对话内容、模型回复、修改建议的值不得写入日志；只记白名单字段。
- 确认保存时必须满足 B-05，确保原始文件与结构化记录关联、一致归档；磁盘使用受控主机/磁盘加密。
- 不得将简历内容或敏感字段写入日志/错误响应；不得把真实简历用于测试。

### Frontend

- 采用工作台已确认的 TypeScript、React 18、Vite、Ant Design；按 `pages → components → hooks → api` 分层，状态使用 React `useState`/`useReducer`。
- 只通过 backend 的 HTTP API 上传、解析、恢复草稿、提交修订和确认；不得直连模型服务、后端存储或外部服务。
- 仅接受 PDF、JPG/JPEG、PNG，单文件不超过 10 MB；不得在浏览器本地存储简历或校对内容。仅使用运行时内存展示；草稿恢复依赖 backend 的安全 HttpOnly Cookie。
- 姓名、手机号、邮箱缺失时引导用户补充；其余字段允许为空；展示识别不确定项并支持对话校对。
- v2：输入区增加文本输入，用于自然语言修改与提问；回复与修改卡片在对话流中展示，修改卡片提供"应用""取消"，不可应用的建议展示原因；等待回复时显示"思考中"。分区就地编辑保留（ADR-006 分区部分、ADR-007）。
- v2：提供历史会话列表（名称、状态、最近活动时间），支持切换、继续、删除（二次确认）；已保存会话只读。
- v2：提供已归档简历页面：列表、详情、打开/下载原始文件；只读，不做搜索。
- v2：对话内容同样只在运行时内存展示，不写入浏览器存储。
- 用户明确确认前不得提示“已保存”；仅在 backend 明确返回保存成功后展示成功反馈。
- API 契约变更须经过 `cross-workbench-reviewer` 审视。
