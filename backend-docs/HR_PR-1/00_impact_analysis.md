## 变更影响评估

### 新增

按 PRD 用户故事与分层给出（数据结构先行，具体字段留 architecture-advisor）：

1. **`schemas`（简历模型 + 草稿模型）**——故事#2/#3
   - 简历模型字段来源 `global-info/简历模板.md`（姓名、求职意向、联系方式、个人信息、个人优势、工作经历[多条]、项目经历[多条]、教育背景[多条]、专业技能、证书与荣誉、语言能力、自我评价）。
   - 需要**字段级状态**，枚举固定为 `recognized`（已识别待确认）/ `uncertain` / `missing` / `confirmed`（C-04），以满足 S2-2、S3-2；backend 只返回字段值 + 状态，不维护校对游标、不生成提示语（C-03）；"保留未确认字段待处理状态"依赖此结构。
   - 请求 / 响应 / 领域模型按 `Request/Response/Dto` 后缀命名（AGENTS.md 命名约定）。
2. **`clients`（DeepSeek 客户端）**——故事#2
   - 唯一外部出口（B-02）；负责超时、重试、日志脱敏（B-03）、凭证来自环境变量（B-01）。
   - 将模型输出约束为简历模型的结构化 JSON，并对非法输出做校验与降级（不静默猜测补全，S2-2）。
3. **`api`（路由）**——故事#1~#4，对应 HLD §4 三条契约（具体路径待技术设计，不在此臆定）
   - 上传并同步解析（multipart/form-data）；重新上传即覆盖当前草稿，不新增丢弃草稿接口（C-07）。
   - 草稿读取 / 校对更新（凭 HttpOnly Cookie 令牌）。
   - 确认并保存：幂等，同键再次确认不新增、返回已有记录并带“已保存过”标识（C-10）。
   - **OpenAPI 先行**：architecture-advisor 阶段须先产出 OpenAPI 草稿，经跨 Workbench Review 冻结后两侧并行开发（C-13）。
   - 统一错误体与异常处理器；`request_id` 中间件。
4. **`services`**
   - 上传服务：类型 / 大小 / 内容校验 → 写临时区 → 生成草稿 + 令牌 → 调模型 → 落草稿。
   - 校对服务：字段更新、字段状态流转、核心三项缺失提示。
   - 归档服务：确认校验 → 按规范化键（姓名、手机号去首尾空格，邮箱去空格并小写）查重 → 命中则返回已有记录（“已保存过”）→ 未命中则文件移入 `file/` → 写 SQLite → 失败补偿（B-05）。
   - 草稿清理服务：7 天无活动清理（ADR-003）；进程启动时 + 简单定时扫描（单进程，C-06）。
   - 校验：后端为权威校验；手机号 = 11 位大陆号或 `+` 开头国际号，邮箱仅格式校验；格式不合法拒绝保存并指出字段，不视同缺失（C-09）。
   - 保存成功后删除草稿与临时文件并作废令牌；已确认记录不可修改（C-11）。
5. **`repositories`**
   - 正式库：简历记录（含工作 / 项目 / 教育等子项的存储方式待设计）+ 原始文件关联（相对路径、原始文件名、类型、大小、可选摘要）；记录与文件一对一（C-02）。**对 (姓名, 手机号, 邮箱) 的规范化值建唯一约束**，兜底并发确认（C-10，替换原“草稿 id 唯一关联”设计）。
   - 临时草稿存储：**独立 SQLite 文件**，与正式库分离（C-12）。
   - 审计字段 `id / created_at / updated_at`（database.md §2）；SQL 参数绑定。
6. **`core`**：配置（环境变量读取密钥、目录、模型名 `deepseek-flash`、模型调用超时 60s（C-08）、Cookie：`HttpOnly; SameSite=Lax; Path=/`，不强制 Secure（C-06））、日志脱敏、应用定时 / 启动清理钩子。
7. **`tests`**：pytest（C-15）；仅合成或脱敏简历（B-06）；模型调用 mock 策略（测试内不得真实外发）。
8. **工程**：uv + `pyproject.toml`（C-15）。

## 技术风险

| 风险 | 严重性 | 说明 |
|------|:-----:|------|
| R-01 `deepseek-flash` PDF / 图像直接输入（C-01：DL 已实测支持，维持 ADR-001，不做 PDF 转图 / 文本提取） | 低 | HLD §8 假设 1。注：跨 Workbench Review 记录公开文档仅列图片格式，故**保留为实现首个 spike**：须留存 PDF 与图片调用的证据（请求形态、响应样例，使用合成简历，脱敏）。本分析未亲自调用验证 |
| R-02 同步解析超时与并发 | 低（POC） | 模型调用超时 60s（C-08），frontend 请求超时 75s，超时后提示重新上传；单进程不做并发限流。须明确超时后草稿状态（建议：保留已上传文件的草稿但无解析结果，或不建草稿——见下方再确认点） |
| R-03 草稿令牌与 Cookie | 低（POC） | 已定（C-06）：localhost 同源，开发用 Vite dev proxy 转发 `/api`；Cookie `HttpOnly; SameSite=Lax; Path=/`，不强制 Secure，有效期 7 天；无需 CORS |
| R-04 B-05 跨"文件系统 + SQLite"无分布式事务 | 高 | 无法原子；需"临时名写入 → 事务提交 → rename"的顺序与失败补偿，并处理进程在中间点崩溃（启动时对账清理）。⚠️ 补偿方案细节待技术设计 |
| R-05 草稿 7 天清理的触发方式 | 低（POC） | 单进程（C-06），启动时 + 简单定时扫描；清理仅作用于草稿库与临时目录，不得触碰 `file/` 正式归档 |
| R-06 模型输出不可信 | 中 | 模型可能返回幻觉字段 / 格式错误，违反"不得猜测补全"。须以 Pydantic 严格校验并把无依据字段置为"不确定" |
| R-07 SQLite 并发写 | 低 | 5 人并发规模下可行，须启用 WAL 与单写连接策略 |
| R-08 文件内容安全 | 中 | 须校验魔数 / MIME；文件名重命名落盘（防路径穿越）。按 C-02 不另设 PDF 页数上限，仅 ≤10 MB，资源耗尽风险由 60s 超时兜底 |
| R-09 个人信息校验 | 低 | 规则已定（C-09）：手机号 11 位大陆号或 `+` 开头国际号，邮箱仅格式校验 |
| R-10 幂等键与“确认成功但响应丢失” | 中 | C-10 幂等键为 姓名+手机号+邮箱。C-11 要求保存后删草稿并作废令牌，而 C-05 允许 frontend 超时后直接重试确认：若首次已成功、响应丢失，重试时令牌已作废/草稿已不存在，无法触达“同键返回已有记录”逻辑。⚠️ 需 DL 再确认处理方式（见汇报） |
