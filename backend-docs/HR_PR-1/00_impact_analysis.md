## 变更影响评估

### 新增

按 PRD 用户故事与分层给出（数据结构先行，具体字段留 architecture-advisor）：

1. **`schemas`（简历模型 + 草稿模型）**——故事#2/#3
   - 简历模型字段来源 `global-info/简历模板.md`（姓名、求职意向、联系方式、个人信息、个人优势、工作经历[多条]、项目经历[多条]、教育背景[多条]、专业技能、证书与荣誉、语言能力、自我评价）。
   - 需要**字段级状态**（已识别 / 不确定 / 缺失 / 用户已确认）以满足 S2-2、S3-2；"保留未确认字段待处理状态"依赖此结构。
   - 请求 / 响应 / 领域模型按 `Request/Response/Dto` 后缀命名（AGENTS.md 命名约定）。
2. **`clients`（DeepSeek 客户端）**——故事#2
   - 唯一外部出口（B-02）；负责超时、重试、日志脱敏（B-03）、凭证来自环境变量（B-01）。
   - 将模型输出约束为简历模型的结构化 JSON，并对非法输出做校验与降级（不静默猜测补全，S2-2）。
3. **`api`（路由）**——故事#1~#4，对应 HLD §4 三条契约（具体路径待技术设计，不在此臆定）
   - 上传并同步解析（multipart/form-data）。
   - 草稿读取 / 校对更新（凭 HttpOnly Cookie 令牌）。
   - 确认并保存。
   - 统一错误体与异常处理器；`request_id` 中间件。
4. **`services`**
   - 上传服务：类型 / 大小 / 内容校验 → 写临时区 → 生成草稿 + 令牌 → 调模型 → 落草稿。
   - 校对服务：字段更新、字段状态流转、核心三项缺失提示。
   - 归档服务：确认校验 → 文件移入 `file/` → 写 SQLite → 失败补偿（B-05）。
   - 草稿清理服务：7 天无活动清理（ADR-003）。
5. **`repositories`**
   - 正式库：简历记录（含工作 / 项目 / 教育等子项的存储方式待设计）+ 原始文件关联（相对路径、原始文件名、类型、大小、可选摘要）。
   - 临时草稿存储：**与正式数据库分离**（HLD §2、§5），形态（独立 SQLite 文件 / 文件系统 JSON）待定，见 Q-backend-02。
   - 审计字段 `id / created_at / updated_at`（database.md §2）；SQL 参数绑定。
6. **`core`**：配置（环境变量读取密钥、目录、模型名 `deepseek-flash`、超时、Cookie 属性）、日志脱敏、应用定时 / 启动清理钩子。
7. **`tests`**：仅合成或脱敏简历（B-06）；模型调用 mock 策略（测试内不得真实外发）。

## 技术风险

| 风险 | 严重性 | 说明 |
|------|:-----:|------|
| R-01 `deepseek-flash` 对 PDF / 图像的实际接入方式（已确认支持，仅余输入形式细节） | 低 | HLD §8 假设 1。⚠️ 待确认：官方 API 是否原生接受 PDF / 图片字节（还是需先转文本 / 图片 URL / base64）。若 API 仅支持文本，而 ADR-001 又禁止 OCR 与其他模型，则"直接理解"路径**不可行**，须回 Dev Lead。本次未能在代码中验证（无代码、无 API 凭证），不下确定性结论 |
| R-02 同步解析超时与并发 | 中 | 约 5 人并发、10 MB、无 SLA（HLD §8 假设 2）。FastAPI 若用同步阻塞调用会占满线程池；须定义客户端超时、并发上限与超时后的草稿状态。⚠️ 待确认超时阈值 |
| R-03 草稿令牌与 Cookie | 中 | 7 天 HttpOnly Cookie（HLD §8 假设 4）。须确定 `Secure` / `SameSite` / `Domain`；前后端若跨源（Vite 开发服务器 vs API）会影响 `SameSite` 与 CORS credentials。⚠️ 待确认部署域名与是否同源 |
| R-04 B-05 跨"文件系统 + SQLite"无分布式事务 | 高 | 无法原子；需"临时名写入 → 事务提交 → rename"的顺序与失败补偿，并处理进程在中间点崩溃（启动时对账清理）。⚠️ 补偿方案细节待技术设计 |
| R-05 草稿 7 天清理的触发方式 | 中 | 进程内定时任务 vs 外部 cron；多 worker 下重复清理；清理不得触碰 `file/` 正式归档（HLD §8 假设 5）。⚠️ 待确认部署形态（单进程 / 多 worker） |
| R-06 模型输出不可信 | 中 | 模型可能返回幻觉字段 / 格式错误，违反"不得猜测补全"。须以 Pydantic 严格校验并把无依据字段置为"不确定" |
| R-07 SQLite 并发写 | 低 | 5 人并发规模下可行，须启用 WAL 与单写连接策略 |
| R-08 文件内容安全 | 中 | 仅校验扩展名不足；须校验魔数 / MIME，限制 PDF 页数与图像像素以防资源耗尽；文件名须重命名（不用用户文件名落盘，防路径穿越） |
| R-09 个人信息校验 | 低 | 手机号 / 邮箱格式规则未定，见 Q-backend-04 |

## 对 requirements 的建议补充

PRD 可能未覆盖的边界条件：

- 用户重复上传 / 在同一草稿上重新上传文件的语义（覆盖草稿还是新建草稿）。
- 同一人（同手机号 / 邮箱）重复提交的简历是否去重或允许多条（见 Q-backend-03）。
- 模型解析失败后，已上传的文件与草稿是否保留供重试。
- 多页 PDF / 多张图片组成一份简历的支持范围（PRD 与 Q2 仅说"单文件"）。
- 确认保存后草稿与临时原始文件的处置（立即删除）及 Cookie 令牌是否作废。
- 超大 / 加密 / 损坏 PDF 的提示口径（统一错误体下的业务码）。
- 校对对话是"逐字段问答"还是"整体表单修改"：影响 backend 是否需要维护"当前校对步骤"状态，见 Q-backend-06。
