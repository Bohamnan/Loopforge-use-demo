## 简介

本模块归属 frontend 应用 `hr-collection-agent-web`（TypeScript / React 18 / Vite / Ant Design），为提供简历的用户提供对话式流程：上传简历 → 展示识别结果 → 逐项校对或对话修改 → 明确确认 → 反馈结果；另提供历史会话栏与已归档简历页（v2）。

- 只通过 backend 接口取数，同源部署（localhost）；开发环境由 Vite dev proxy 转发 `/api`（C-06）。
- 状态只用 `useState` / `useReducer` 保存在运行时内存，不引入额外的状态管理库。
- 范围外：简历筛选与评价、账号与权限、已归档简历的编辑与删除（更新只经 REQ-FE-09）、路由库与深链接。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
- v2 依据：PRD v2/v2.1；HLD v2/v2.1；ADR-006（v2 修订）、ADR-007/008/009；跨 Workbench 裁决 X-01..X-10a、Y-01、Y-02；第二轮 TQ-v2-F01..F14；影响分析 v2（第 1–11 节）。
- 依据：PRD `01-requirements/HR_PR-1/prd.md`；第一轮 Q&A Q1..Q8 与第二轮 TQ-01..TQ-13（`requirements_plan.md`）；HLD `solution-design.md`；跨 Workbench 裁决 C-01..C-15、D-01..D-06（`01-requirements/HR_PR-1/cross-workbench-review.md`）；影响分析 `00_impact_analysis.md`（v1.1）。

## 术语表

| 术语 | 说明 |
|------|------|
| 简历模型 | 以 `global-info/简历模板.md` 为准的结构化字段集合，"语言能力"为独立分类（C-14） |
| 原始文件 | 用户上传的简历文件（PDF、JPG/JPEG、PNG） |
| 校对 | 用户在对话中逐项确认、修正、补充字段的过程；确认后才保存 |
| 未确认草稿 | 用户确认前由 backend 暂存的简历数据，属于某个会话；前端不在浏览器本地保存 |
| 会话 | 一次简历提交过程，含草稿、对话记录与修改建议；状态"校对中"/"已保存"；同一浏览器可在历史会话栏查看、切换、删除（v2） |
| 浏览器标识 | backend 下发的 HttpOnly Cookie，前端不读不写；用于列出本浏览器的会话（v2，替代 v1 草稿访问令牌） |
| 修改建议 | 对话中模型给出的字段修改提议，用户"应用"后才生效（v2） |
| 更新候选 | "已保存过"时冻结保留的本次内容，用户再次确认后覆盖已有简历（v2.1） |
| 字段状态 | `recognized`（已识别，待确认）/ `uncertain`（不确定）/ `missing`（缺失）/ `confirmed`（已确认）（C-04） |
| 已保存过 | backend 判定同一个人（姓名 + 手机号 + 邮箱）已有简历记录时返回的结果，带 `already_saved` 标识；v2.1 起展示已有内容并可确认更新（C-10、X-06） |

## 需求

### REQ-FE-01：上传 PDF 或照片简历

**用户故事：** 作为提供简历的用户，我希望在对话界面中上传简历文件，以便系统识别内容。

**关联 PRD：** 用户故事#1；Q2；TQ-02（C-08）、TQ-06（C-07）

#### 验收标准

1. THE 上传控件 SHALL 只允许选择单个 PDF、JPG、JPEG 或 PNG 文件。
2. IF 所选文件类型不支持或超过 10 MB, THEN THE 前端 SHALL 在上传前提示并阻止提交；backend 的校验结果为最终结论。
3. WHEN 文件提交上传, THE 前端 SHALL 显示单一加载提示，并在等待期间禁止重复提交。
4. IF 上传请求超过 75 秒未返回, THEN THE 前端 SHALL 结束等待，提示用户重新上传（C-08）。
5. WHEN 用户在任意会话中上传新文件, THE 前端 SHALL 视为新建会话并在成功后切换过去，原会话保留在列表中；不再弹出覆盖确认（TQ-v2-F06）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
6. IF backend 返回上传错误（类型、大小、内容不符或模型不可用）, THEN THE 前端 SHALL 只展示错误体中的 `message`，不展示或记录文件内容。

### REQ-FE-02：展示简历模型识别结果

**用户故事：** 作为提供简历的用户，我希望清楚看到系统识别出的各项信息及其状态，以便知道哪些需要我处理。

**关联 PRD：** 用户故事#2；Q1、Q3；TQ-01（C-04、C-14）

#### 验收标准

1. WHEN 上传成功或读取校对中的会话成功（v2）, THE 前端 SHALL 按简历模型的全部分类展示字段，其中工作经历、项目经历、教育背景按多条展示。
2. THE 前端 SHALL 按字段状态区分展示：`recognized` 显示为"待确认"，`uncertain` 显示为"不确定、请确认"，`missing` 显示为"待补充"，`confirmed` 显示为"已确认"。
3. THE 前端 SHALL 不把 `recognized` 字段当作已确认展示，也不自行补全任何字段的值（B-04、C-04）。
4. THE 前端 SHALL 允许非核心字段为空，只把姓名、手机号、邮箱作为保存门槛。

---

### REQ-FE-03：对话式逐项校对

**用户故事：** 作为提供简历的用户，我希望系统逐项向我确认信息，我可以直接修正或补充。

**关联 PRD：** 用户故事#2、#3；Q3；TQ-04（C-03）、TQ-05（C-09）

#### 验收标准

1. THE 前端 SHALL 按简历模板的 22 个字段划分分区，按固定顺序逐区核对：每个分区展示该区全部字段及其状态，并突出 `missing` 与 `uncertain` 字段；用户确认该区后，对该区字段提交结构化更新（C-03、O-11、P-04）。
2. WHEN 用户对某一字段确认、修正或补充, THE 前端 SHALL 以结构化字段编辑的形式提交给 backend，并以 backend 返回的结果更新界面；其余字段保持原状态。
3. THE 前端 SHALL 支持对工作经历、项目经历、教育背景等多条子项进行新增、修改和删除。
4. WHEN 姓名、手机号或邮箱缺失, THE 前端 SHALL 引导用户补充。
5. WHEN 用户输入手机号或邮箱, THE 前端 SHALL 使用与 backend 相同的规则即时提示格式问题：手机号为 11 位大陆号或以 `+` 开头的国际号，邮箱只校验格式（C-09）。
6. IF backend 返回带 `details` 的字段级错误, THEN THE 前端 SHALL 在对应字段旁展示原因（D-06）。

### REQ-FE-04：明确确认并反馈保存结果

**用户故事：** 作为提供简历的用户，我希望只在我明确确认后才保存，并清楚知道保存结果。

**关联 PRD：** 用户故事#4；Q4；TQ-07（C-05、C-10）、TQ-08（C-11）、TQ-10..TQ-13（D-01、D-03、D-04、D-06）

#### 验收标准

1. THE 前端 SHALL 提供独立的"最终确认"操作；只有当姓名、手机号、邮箱齐全、格式合法并已确认时才可点击（D-03、D-06）。
2. WHEN 仍有未确认字段时用户点击最终确认, THE 前端 SHALL 先提示存在未确认字段；用户继续确认即视为确认当前显示的全部内容（D-03）。
3. THE 前端 SHALL 在 backend 返回保存成功之前，不显示"已保存"或任何成功提示，也不做乐观更新（F-03）。
4. WHEN backend 返回保存成功, THE 前端 SHALL 显示"已保存"与保存成功卡（姓名、原始文件名、保存时间），提供"上传下一份"（即新对话）入口；该会话保留并转为只读的已保存视图（ADR-008、P-09）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
5. WHEN backend 返回 `already_saved` 标识, THE 前端 SHALL 显示"该简历已保存过"，并在其下以只读方式展示已有记录内容，不展示记录编号；同时在对话流中提供快捷回复"按本次内容更新"（见 REQ-FE-09）（X-06、Y-01）。<!-- 变更 v2.1，驱动 HR_PR-1-CRv2.1 -->
6. IF 确认请求超时或网络失败, THEN THE 前端 SHALL 不提示成功，并允许用户直接重试确认；不调用任何保存状态查询接口（C-05）。
7. IF backend 返回"会话不存在"业务码, THEN THE 前端 SHALL 提示该会话已不存在，回到空态并刷新会话列表（v2 替代 D-01）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
8. THE 前端 SHALL 在确认请求进行期间防止重复点击。
9. WHEN 用户在对话中表示"确认提交", THE 前端 SHALL 只展示回复文本，由用户点击现有的确认入口完成保存；对话内容不触发保存（X-02、PRD #4）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
10. WHEN 会话为已保存, THE 前端 SHALL 不显示最终确认入口（只读视图）；IF backend 拒绝对已保存会话的确认, THEN SHALL 只展示错误 `message`（PRD #6，澄清 v2.0.1）。<!-- 变更 v2.0.1：QA 5q 澄清，驱动 HR_PR-1-CRv2 -->

### REQ-FE-05：历史会话<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->

**用户故事：** 作为提供简历的用户，我希望在同一浏览器看到历史会话，继续未完成的校对，查看已保存的内容，或删除会话。

**关联 PRD：** 用户故事#3、#6；Q6；ADR-008；TQ-v2-F01、TQ-v2-F06、TQ-v2-F07；X-03、X-04

#### 验收标准

1. WHEN 页面打开, THE 前端 SHALL 读取会话列表并展示空态（新对话），不自动打开任何会话；fetch 使用 `same-origin`，前端不读取 Cookie（TQ-v2-F07、C-06）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
2. THE 会话列表 SHALL 展示 backend 给出的会话名称、状态（校对中/已保存）、最近活动时间，顺序以 backend 为准；窄屏下列表仍可到达（X-04）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
3. WHEN 用户选择会话, THE 前端 SHALL 读取该会话：校对中会话可继续校对与对话；已保存会话以只读方式展示对话记录与简历内容（PRD #6、X-07）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
4. WHEN 用户切换会话或新建对话且有未提交的分区编辑, THE 前端 SHALL 先提示"未提交的修改将丢失"；无未提交编辑时直接切换（P-08 v2 调整）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
5. WHEN 用户删除会话, THE 前端 SHALL 二次确认，文案按状态区分（校对中：简历信息与文件一并删除；已保存：只删对话，归档仍可查看）；成功后从列表移除，删除当前会话则回到空态（PRD #6、X-03）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
6. THE 前端 SHALL 在上传、对话、应用/取消、保存、更新、删除成功后重新读取会话列表。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->

### REQ-FE-06：浏览器侧数据安全与接口规范

**用户故事：** 作为系统，我希望前端不保存敏感数据、不直连外部服务，并统一处理接口结果。

**关联 PRD：** 用户故事#1–#4（横切）；架构约束 F-01..F-03、B-03；`rules/frontend/api.md`；TQ-01（C-13）、TQ-09（C-15）

#### 验收标准

1. THE 前端 SHALL 只通过统一的 api 封装调用 backend `/api/v1` 接口，不持有任何凭证，不直连模型或其他外部服务（F-01）。
2. THE 前端 SHALL 不使用 localStorage、sessionStorage 或 IndexedDB 保存简历、校对、对话内容或会话列表；文本输入框关闭自动填充；原始文件的临时 blob URL 用后即回收（F-02）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
3. THE 前端 SHALL 不在控制台或日志中输出简历内容、对话内容或接口响应体，也不把姓名等写入页面标题、URL 或下载文件名；下载原始文件时使用通用文件名（如"原始简历.pdf"）（B-03、v2.0.1 澄清）。<!-- 变更 v2，驱动 HR_PR-1-CRv2 -->
4. THE 前端 SHALL 把错误统一解析为 `{code, message, request_id}`，以及可选的 `details: [{field, reason}]`（D-06）。
5. THE 前端的 types 与 api 层 SHALL 在 backend OpenAPI 草稿冻结后与之对齐；冻结前只搭骨架（C-13）。
6. THE 前端测试 SHALL 使用 Vitest 与 React Testing Library，代码检查使用 ESLint，测试数据只用合成简历（C-15、B-06）。

### REQ-FE-07：对话修改与问答 <!-- 变更 v2，驱动 HR_PR-1-CRv2 -->

**用户故事：** 作为提供简历的用户，我希望直接在对话中说明修改或提问，并在确认后应用修改。

**关联 PRD：** 用户故事#3（v2 条目）、#5；ADR-007；TQ-v2-F02、TQ-v2-F03、TQ-v2-F05；X-01

#### 验收标准

1. WHEN 当前会话为校对中, THE 输入区 SHALL 提供文本输入与发送（Enter 发送、Shift+Enter 换行，输入法组合时 Enter 不发送）；单条最长 2000 字符；未上传或已保存的会话禁用并说明原因。
2. WHEN 消息发送中, THE 前端 SHALL 在对话流末尾显示"思考中"，并禁用上传、分区编辑、切换与再次发送。
3. THE 前端 SHALL 将对话请求超时设为 75 秒；IF 请求失败或超时, THEN SHALL 保留用户原文并提示可重试，重试前先重新读取会话核对是否已成功，已有简历与对话不受影响（X-01、PRD #5）。
4. WHEN 回复包含修改建议, THE 前端 SHALL 以卡片逐项展示字段名称、原值、新值（文本列表字段展示完整新列表），提供"应用""取消"；不可应用项不显示"应用"并展示原因（PRD #3、TQ-v2-F02）。
5. WHEN 用户点击"应用", THE 前端 SHALL 以 backend 返回的结果更新分区展示，卡片显示"已应用"；有同字段未提交的分区编辑时以应用结果为准并清除该编辑；失败时卡片保持待处理并可重试。
6. THE 前端 SHALL 不自行解析用户文本的意图，建议的状态以 backend 为准；重新打开会话时按 backend 返回的状态展示已应用/已取消。
7. THE 分区就地编辑 SHALL 保留，与对话修改作用于同一份简历信息（ADR-006 分区部分）。

### REQ-FE-08：已归档简历页 <!-- 变更 v2，驱动 HR_PR-1-CRv2 -->

**用户故事：** 作为使用者，我希望查看所有已保存的简历和原始文件。

**关联 PRD：** 用户故事#7；ADR-009；TQ-v2-F08、TQ-v2-F09；X-05、X-07

#### 验收标准

1. THE 前端 SHALL 在外壳中提供"对话 / 已归档简历"切换，不引入路由库；切换不丢失对话页的当前会话、未提交编辑与输入内容。
2. WHEN 进入已归档简历页, THE 前端 SHALL 重新读取列表，展示姓名、手机号、邮箱、求职意向岗位、保存时间；无记录时提示"暂无记录"；不提供搜索、编辑与删除。
3. WHEN 用户选择某条简历, THE 前端 SHALL 按简历模型分类只读展示完整信息（不显示字段状态，未填写的字段显示"未填写"），以及原始文件名、保存时间、最近更新时间。
4. WHEN 用户打开原始文件, THE 前端 SHALL 经 api 层以二进制方式获取并打开或下载；IF 详情标示文件不可用或获取失败, THEN SHALL 页面内提示"原始文件暂不可用"，简历信息仍可查看（X-05）。

### REQ-FE-09：已保存过后的确认更新 <!-- 变更 v2.1，驱动 HR_PR-1-CRv2.1 -->

**用户故事：** 作为提供简历的用户，我希望在提示"已保存过"后，看清这次内容与已有内容的差异，再决定是否更新。

**关联 PRD：** 用户故事#4（v2.1 条目）、#6（v2.1 条目）；ADR-004（v2.1 修订）；TQ-v2-F11..F14；Y-01、Y-02

#### 验收标准

1. WHEN 会话存在更新候选, THE 前端 SHALL 在对话流中"已保存过"提示下提供快捷回复"按本次内容更新"；该会话不开放自由文本输入（Y-01）。
2. WHEN 用户点击快捷回复, THE 前端 SHALL 逐字段比较 backend 返回的已有内容与本次内容，展示差异卡片：列出有差异的字段（原值/新值），本次为空将清空已有值的字段必须列出，同时展示原始文件的新旧名称；相同字段只给出数量（Y-02）。
3. THE 差异卡片 SHALL 提供"确认更新"与"取消"；只有点击"确认更新"才发送更新请求，对话文字不触发更新；请求中防止重复点击。
4. THE 前端 SHALL 仅在更新请求成功且响应形状校验通过后显示"已更新"并重新读取会话；IF 明确失败, THEN SHALL 提示"已有简历未改变"并保留差异卡片；IF 超时或结果未知, THEN SHALL 提示无法确认是否已更新，引导重新打开会话核对（F-03、TQ-v2-F14）。
5. WHEN 用户取消, THE 前端 SHALL 关闭差异卡片，已有内容保持不变。
